# Deploy: Vercel + Render

Production topology:

- **Vercel**: Next.js UI at the public application URL.
- **Render `signal-api`**: HTTP API only.
- **Render `signal-worker`**: connector/job worker.
- **Render `signal-scheduler`**: schedules connector jobs.
- **Render PostgreSQL**: private database.
- Browser requests remain same-origin: `/api/*` on Vercel is rewritten to Render.

## 1. Push this folder to GitHub/GitLab

The repository root must be this folder (the folder containing `package.json`, `render.yaml`, and `next.config.ts`).

## 2. Create the Vercel project once to reserve the public URL

Import the repository into Vercel.

Framework: Next.js.
Build command: `npm run build` (default detection is also fine).
Install command: `npm ci`.
Node.js: `22.x` (pinned by `package.json`).

For this first deployment, `BACKEND_URL` may be left unset. The purpose is to obtain the stable Vercel production URL, for example:

`https://your-project.vercel.app`

Do not use the application yet; the production API is created in the next step.

If you already own the final custom domain, you can use that instead.

## 3. Create the Render Blueprint

In Render, create a Blueprint from the same repository. `render.yaml` creates:

- `signal-api`
- `signal-worker`
- `signal-scheduler`
- `signal-db`

During creation set:

- `APP_URL` = the Vercel production URL from step 2 (or your final custom domain), **without a trailing slash**.
- `OWNER_EMAIL` = initial owner email.
- `OWNER_PASSWORD` = initial owner password, at least 12 characters.

`ENCRYPTION_KEY` is generated by Render and shared with the worker.

After the first successful bootstrap, you may remove `OWNER_PASSWORD` from Render. The bootstrap is idempotent: future deploys only require the password if that owner does not already exist.

Health check:
`https://<your-render-api>/api/health`

Expected response:
`{"ok":true}`

## 4. Connect Vercel to Render

Copy the public URL of `signal-api`, then add this Vercel environment variable:

`BACKEND_URL=https://<your-render-api>.onrender.com`

Do not add a trailing slash.

Redeploy Vercel after setting `BACKEND_URL`.

## 5. Critical URL pairing

These two settings must agree:

- Render `APP_URL` = the Vercel URL users actually open.
- Vercel `BACKEND_URL` = the Render API URL.

Example:

Render:
`APP_URL=https://signal.example.com`

Vercel:
`BACKEND_URL=https://signal-api.onrender.com`

The browser calls `https://signal.example.com/api/...`; Vercel proxies that request to Render. Authentication cookies therefore remain attached to the Vercel/public app domain.

## 6. Smoke test

1. Open the Vercel URL.
2. Sign in with `OWNER_EMAIL` / `OWNER_PASSWORD`.
3. Open `/api/health` on the Vercel domain; expect `{"ok":true}`.
4. Open Sources and run Mock Studio sync.
5. Confirm listings appear.
6. Check Render logs for `signal-worker` and `signal-scheduler`.
7. Create/update a pipeline item and reload to confirm persistence.

## Local development

Without `BACKEND_URL`, Next.js keeps using the existing in-process route handler (`app/api/[...path]/route.ts`), so the original local Docker/dev workflow still works.

To test the split topology locally, run the backend separately on port 4000 and point Next at it:

Backend:
`PORT=4000 node --env-file=.env server/http.mjs`

Frontend environment:
`BACKEND_URL=http://localhost:4000`

Then run:
`npm run dev`
